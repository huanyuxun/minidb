# 崩溃恢复验证

`recovery_test` 启动独立子进程执行事务，再通过 `MINIDB_CRASH_POINT` 在指定持久化边界调用 `_Exit(86)`，跳过 C++ 析构和正常关闭。Windows 使用 `CreateProcessW`，Linux 使用 `fork`/`exec`，不依赖 shell 模拟异常。

每个场景先建立表、主键和二级索引，写入一条基线记录并执行 Checkpoint。测试事务修改原有行，再写入 40 条 400 字节字符串记录，覆盖多个 Heap 和索引页面。父进程要求子进程确实以 86 退出；随后重新打开数据库两次，检查记录数量、旧行值、主键查询和二级索引范围查询。

| 故障点 | 注入位置 | 恢复预期 |
| --- | --- | --- |
| `uncommitted` | 测试程序在 COMMIT 调用之前退出 | 仅基线数据 |
| `wal_partial` | 首个页面映像日志仅写入一半并同步 | 仅基线数据 |
| `wal_flushed` | 页面日志已同步，提交记录尚未写入 | 仅基线数据 |
| `before_commit` | 提交记录之前 | 仅基线数据 |
| `commit_flushed` | 提交记录已同步，数据页尚未写入 | 全部事务修改 |
| `data_write` | 数据页仅写入前 2048 字节并同步 | 全部事务修改，WAL 修复撕裂页 |
| `checkpoint` | 数据页和 Checkpoint 记录已同步，WAL 尚未截断 | 全部事务修改 |

其他检查：

- 在有效提交 WAL 后追加 7 字节不完整日志尾部，验证先前提交仍可恢复。
- 翻转完整 WAL 记录中的一字节，要求校验失败并拒绝打开，不把完整损坏记录当成普通截断。
- Checkpoint 后翻转数据页字节，要求检测损坏；没有可用 WAL 时不声称能修复任意介质损坏。
- 父进程持有数据库文件锁时，另一个进程打开相同数据库必须失败。

这些是实际进程终止和文件字节故障测试；它们不等价于物理断电实验。持久性依赖操作系统同步接口及存储设备履行持久化承诺。校验和用于检测意外损坏，不提供恶意篡改防护。

运行：`ctest --test-dir build -C Release -R recovery --output-on-failure`。具体通过情况和性能数据以交付的测试结果报告为准。
